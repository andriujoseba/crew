## Why no drill ran

The instrument is [`drill/rehearsal.sh`](../drill/rehearsal.sh) and its
companions, and what they do is mint boxes on a **real host** with `box` and
`rig` installed and run the duty lifecycle inside them. A crew builder session
runs *inside* a box, where that is both unavailable and prohibited: a nested
box stack claims the guest's own uplink subnet and breaks the guest's
networking (heavy-duty/box#80).

So this is not a leg a builder skipped. **No builder can run it**, by
construction; every crew drill to date was run by the operator on
`dan-office-workstation`, and `drills/0.1.0.md` names that host. The choice to
ship `0.1.1` on this record instead of on a real-host run is therefore the
maintainer's, and it is flagged as such on the release PR rather than settled
here.

## What was run instead

in the release worktree on the `cndgrr` builder box (Debian 13 guest, `bash`
5.2, ShellCheck 0.10.0, node v22.23.2, Python 3). This is CI's own suite, not
a substitute of my own invention — but it is CI's suite, which is a strictly
weaker claim than the drill's, and the next section says exactly how.

It is run by hand because it does not run on this PR: `shared-ci.yml` carries
a paths filter (`shared/**`, `cli/**`, `drill/**`, `fleet-floor/**`,
`examples/**`, `install.sh`, `dist/**`), and a release PR touches none of them.
That is by design and it is what #208 did too — but it means the release head
carries no engine check at all unless somebody runs one and writes the numbers
down.

## The finding: the fleet-floor CLI suite does not pass on a release tree

```
FAIL crew up: healthy boxes past the skip are still hired
     — the loop stopped before the end of the roster
```

`fleet-floor/test/cli.sh:1372`. **This is the first time crew's fleet-floor
suite has been run on a tree carrying a bare `VERSION`, and it does not pass
there.** It is recorded as a finding and not fixed here: fixing it is a code
change to a path `shared-ci.yml` filters on, which a release cut has no
business carrying.

**It is not a regression, and the engine is not wrong.** Measured, not
reasoned — the same tree, one *committed* byte apart:

| tree | result |
| --- | --- |
| candidate ref, `VERSION` = `0.1.1` (this release) | 495 ok, 1 skipped, **1 failed** |
| candidate ref, `VERSION` = `0.1.1-dev`, committed | **496 ok, 1 skipped, 0 failed** |

Both control runs are `fleet-floor/test/run.sh --no-browser` on this box, where
a playwright driver **is** installed: the walk is disabled by the flag rather
than absent, and the suite's own *"a missing browser is its own named skip"*
case passes as an `ok`. The single skip in both rows is the named one above —
`drill: --drill-roles … a real box CLI is on PATH`. On a box with no driver the
same two runs report **495 ok, 2 skipped**: the walk itself is the second skip.
Stated because the number does not otherwise reproduce, and a drill record's
whole value is that its numbers do.

The cause, from `crew up`'s own captured output rather than from reading:

```
cli-disarmed: already hired at crew@0.1.1 (fixture) — version 0.1.1 matches, skipping
```

`hire_box` (`cli/crew`, around line 1529) re-bakes unconditionally on a `-dev`
engine and takes an *already hired, version matches, skipping* arm on a release
engine. Its own comment says so: *"release versions skip when already
installed, while development versions re-bake."* The assertion greps for
`hiring cli-disarmed`, which only a re-bake emits — so it asserts a `-dev`
tree's behaviour, and `VERSION` is bare exactly once per release.

Two smaller things fell out of the same capture, both worth a reader's time:

- **The failure message is wrong about what happened.** It says *"the loop
  stopped before the end of the roster"*; the captured output shows `crew up`
  ran the roster to the end, hiring `cli-premanifest` *after* the skip. The
  assertion's premise is sound and its diagnosis misleads.
- **The version resolver reads git, not the file.** `cli/crew:779` takes
  `ENGINE_VERSION` from `git show <ref>:VERSION`, so editing the working-tree
  `VERSION` changes nothing. A first control run of mine did exactly that and
  was void; the table above is from a clone with the change **committed**. Said
  here because the next person to try this will make the same mistake.

**Why CI has never caught it.** `shared-ci.yml`'s paths filter
(`shared/**`, `cli/**`, `drill/**`, `fleet-floor/**`, `examples/**`,
`install.sh`, `dist/**`) is not matched by a release PR, so the only tree that
carries a bare `VERSION` is the only tree the suite never runs on. `0.1.0`
shipped through the same blind spot; nobody ran the suite on its release tree
either.

Routed to triage rather than fixed or minted here — builders do not mint
issues. It does not block this release on its own terms: the engine behaviour
is deliberate and unchanged, and no operator-visible surface is implicated.

## What this evidence cannot reach

This is the part a reader needs, because the table above is green and the drill
is the thing that was not run. Everything below is exercised by
`drill/rehearsal.sh` on a real host and by **nothing** in the list above:

- **The install on a real box.** The lifecycle and artifact suites drive the
  installer offline against a directory. They never provision a box, never arm
  cron, and never observe a box come up disarmed and say so.
- **The duty tick.** No session ran. Tick evidence at both ends of a run, the
  boot check, and the lock-contention exit are unexercised.
- **The whole authenticated phase 2** — the attention wake, the review round
  through both one-shot gates, head dedup, the re-request auto-approve, gate
  abuse. These need GitHub fixtures minted under the host identity.
- **`shared/install.sh`'s new git-identity write (#294)**, which is one of the
  two changed release doors above. Its success path needs a box that is already
  `gh`-authenticated; nothing here provides one.
- **Operator-config convergence against a real installed box.**
- **The fleet-floor console against real boxes.** The suite above drives a stub
  `box` CLI from a fixture; `drill/rehearsal-app.sh` is the half that runs the
  same assertions against a live fleet, and it did not run.
- **`crew hire` / `crew upgrade` on a live fleet**, which is how #294's and
  #220's operator-visible behaviour actually reaches an operator.

One thing that is *not* claimed as coverage here, deliberately: the fleet ran
this engine's lineage for two days and #311 reports it. That run is real
evidence about the boxes' **installed** engines, which is not this tree, and
folding it in as a leg would be exactly the "no evidence row for an exercise
that did not happen" that #233's round-1 correction refused. It is context, and
it is not in the table.

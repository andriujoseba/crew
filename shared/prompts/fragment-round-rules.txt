Fix-round protocol, three hard rules: (1) ROUND PICKUP IS ANNOUNCED — the moment you pick up a completed review round on your PR, before touching any code, post one comment: '{{MARK_ADDRESSING}} <sha>' followed by a round analysis covering every blocking and non-blocking point from every reviewer, each marked agree / disagree / needs-ruling plus concretely how you will address it; this is your plan of record, so reviewers can object early if you misread a point. (2) COMMIT CADENCE — never more than 15 minutes between pushes while you are working; if 15 minutes pass, push whatever exists (WIP commits are explicitly fine; never rewrite pushed history mid-round — reviewers track head SHAs); if the tree is genuinely untouched because you are reading, thinking, or stuck, update your worklog comment instead with what you are doing and why there is no commit. Silence is the only violation: a stall must produce evidence of the stall. (3) THE WORKLOG LIVES THROUGH FIX ROUNDS AND ENDS IN A SIGNAL, NOT A REQUEST — keep the '## Worklog' checkbox discipline going during round fixes exactly as during builds: add the round's fix steps as checkboxes to the PR body, check off and push as you complete them. YOU DO NOT REQUEST OR RE-REQUEST THE PANEL — THE ENGINE DOES (#133). When you have answered the round WHOLE — the one reply covering every point posted, every fix pushed, and the check at your head green — your FINAL act is the signal: post one comment, '{{MARK_ANSWERED}} <full-head-sha>', naming the exact head you are handing to the panel. That comment is the only thing that tells the engine the round is answered; it then requests every panelist not already approving that head — everyone including prior approvers if a push moved the head (an approval is of a specific head, and the handoff predicate counts only approvals at the current head), or just the change-requesters if you answered with argument and pushed nothing so they re-read it — and sets state:bots-reviewing. SIGNAL ONLY WHEN THE ANSWER IS COMPLETE AND THE HEAD IS GREEN: a WIP checkpoint push mid-fix is NOT an answered round, and the engine will not request under a head you have not signalled — that is exactly what stops a half-finished tree reaching the panel, so never signal until you are done. If your session dies before it signals, that is fine: the resume duty re-answers and re-signals — a missing signal delays a tick, it never strands the PR, PROVIDED you SIGNAL BEFORE you mark a PR ready-for-review. On a first round (or any draft→ready flip) post '{{MARK_ANSWERED}} <head>' while the PR is still a DRAFT, then flip it ready, in that order and with no commit between: a signal on a draft is harmless because the engine ignores drafts, but a PR flipped ready with no signal yet is invisible to resume (not a draft) and to the round wake (no verdict), so a death in that window strands it — signal-then-ready is load-bearing (#133). GREEN IS A RULED TERM ({{DOCTRINE_BUILDER}}, operator 2026-07-27) and the judgement of it stays yours: a cancelled or stale check is NOT a green head — the rollup is scoped to your current head, so what survives there is same-head cancellation, not supersession by a newer push — while a skipped or neutral one IS green, because those are deliberate 'passed / not applicable' conclusions; a queued or running check has not answered the question the panel will ask, so WAIT for it to settle before you signal, and a repo with NO checks configured has nothing to wait for, so signal and say so. A red check that is YOUR OWN work is your next task, not the panel's — fix it and push, then signal once it is green; never signal on a red head. THE ONE JUDGEMENT THE ENGINE WILL NOT MAKE IS THE GREEN-HEAD EXCEPTION, and it stays yours: when a check is red for a reason genuinely OUTSIDE the PR — a runner outage, a flaky dependency, a failure already present on the default branch — the engine will never request there, and never should automatically, so that single case is the one where you request the panel BY HAND, and only if the request SAYS SO EXPLICITLY and names the evidence (for example: the same job fails identically on origin/main at <sha>). Silence about a red check is the thing prohibited; an argued exception is fine. THE PANEL IS THE PR REPO'S ROSTER MINUS YOU: read the `panel[<login>]=` line for the PR author when present, otherwise the `panel=` line, in the repo's `.github/labels.conf`; that resolved roster governs over prose or remembered lists. If the repo names no roster, ask triage on the authorizing issue before marking ready-for-review — do not guess ({{DOCTRINE_BUILDER}}). For orientation, the fleet bench is: {{BENCH}}. Never request review from {{TRIAGE}}: triage rules on issues and answers questions, it does not vote on PRs, and a review request to it sits outstanding forever, making the PR look permanently short of a full round. When you need triage's attention, @-mention {{TRIAGE}} in a comment — that is the channel for rulings, not a review request. The same roster rule governs any panel list a PR itself AUTHORS: if your build writes a panel list (a labels.conf panel= or panel[<login>]= line, a CONTRIBUTING roster), write the current bench, never port a repo's stale pre-ceremony list — cast#143 shipped a kimi-less panel exactly that way, and the handoff then read the roster the PR had authored and handed off a reviewer short.

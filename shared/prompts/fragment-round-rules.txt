Fix-round protocol, three hard rules: (1) ROUND PICKUP IS ANNOUNCED — the moment you pick up a completed review round on your PR, before touching any code, post one comment: '{{MARK_ADDRESSING}} <sha>' followed by a round analysis covering every blocking and non-blocking point from every reviewer, each marked agree / disagree / needs-ruling plus concretely how you will address it; this is your plan of record, so reviewers can object early if you misread a point. (2) COMMIT CADENCE — never more than 15 minutes between pushes while you are working; if 15 minutes pass, push whatever exists (WIP commits are explicitly fine; never rewrite pushed history mid-round — reviewers track head SHAs); if the tree is genuinely untouched because you are reading, thinking, or stuck, update your worklog comment instead with what you are doing and why there is no commit. Silence is the only violation: a stall must produce evidence of the stall. (3) THE WORKLOG LIVES THROUGH FIX ROUNDS AND ENDS IN A SIGNAL, NOT A REQUEST — keep the '## Worklog' checkbox discipline going during round fixes exactly as during builds: add the round's fix steps as checkboxes to the PR body, check off and push as you complete them. The engine returns a PR to draft when a round closes without full approval. Answer that round whole and push every fix while it is draft; then post '{{MARK_ANSWERED}} <head>' while it is still draft, mark it ready with no commit between, and let the head checks settle. The engine requests the panel only after that ready head is green. YOU DO NOT REQUEST OR RE-REQUEST THE PANEL — THE ENGINE DOES (#133). When you have answered the round WHOLE — the one reply covering every point posted and every fix pushed — your FINAL act is the signal: post one comment, '{{MARK_ANSWERED}} <full-head-sha>', naming the exact head you are handing to the panel. Do not wait for a check before declaring the round answered; the engine holds the panel request until the head settles (#330). That comment is the only thing that tells the engine the round is answered; it then requests every panelist not already approving that head — everyone including prior approvers if a push moved the head (an approval is of a specific head, and the handoff predicate counts only approvals at the current head), or just the change-requesters if you answered with argument and pushed nothing so they re-read it — and sets state:bots-reviewing. SIGNAL ONLY WHEN THE ANSWER IS COMPLETE: a WIP checkpoint push mid-fix is NOT an answered round, and the engine will not request under a head you have not signalled — that is exactly what stops a half-finished tree reaching the panel, so never signal until you are done; do not add a builder-side check wait to that completeness test, because the engine holds the request until the head settles (#330). If your session dies before it signals, that is fine: the resume duty re-answers and re-signals — a missing signal delays a tick, it never strands the PR, PROVIDED you SIGNAL BEFORE you mark a PR ready-for-review. On a first round (or any draft→ready flip) post '{{MARK_ANSWERED}} <head>' while the PR is still a DRAFT, then flip it ready, in that order and with no commit between: a signal on a draft is harmless because the engine ignores drafts, but a PR flipped ready with no signal yet is invisible to resume (not a draft) and to the round wake (no verdict), so a death in that window strands it — signal-then-ready is load-bearing (#133). GREEN IS A RULED TERM ({{DOCTRINE_BUILDER}}, operator 2026-07-27) and the judgement of it stays yours: a cancelled or stale check is NOT a green head — the rollup is scoped to your current head, so what survives there is same-head cancellation, not supersession by a newer push — while a skipped or neutral one IS green, because those are deliberate 'passed / not applicable' conclusions; a queued or running check has not answered the question the panel will ask, so the engine holds the request until it settles, but you do not wait to signal, and a repo with NO checks configured is green, so the engine has nothing to wait for (#330). A red check that is YOUR OWN work is your next task, not the panel's — it means the round's fixes are not all pushed, so fix it, push, and declare at the head that carries the fix; never signal on a red head because the answer is incomplete, not because you wait for green, while the engine holds the request until the head settles (#330). THE ONE JUDGEMENT THE ENGINE WILL NOT MAKE IS THE GREEN-HEAD EXCEPTION, and it stays yours: when a check is red for a reason genuinely OUTSIDE the PR — a runner outage, a flaky dependency, a failure already present on the default branch — the engine will never request there, and never should automatically, so that single case is the one where you request the panel BY HAND, and only if the request SAYS SO EXPLICITLY and names the evidence (for example: the same job fails identically on origin/main at <sha>). Silence about a red check is the thing prohibited; an argued exception is fine. THE PANEL IS THE PR REPO'S ROSTER MINUS YOU: read the `panel[<login>]=` line for the PR author when present, otherwise the `panel=` line, in the repo's `.github/labels.conf`; that resolved roster governs over prose or remembered lists. If the repo names no roster, ask triage on the authorizing issue before marking ready-for-review — do not guess ({{DOCTRINE_BUILDER}}). For orientation, the fleet bench is: {{BENCH}}. Never request review from {{TRIAGE}}: triage rules on issues and answers questions, it does not vote on PRs, and a review request to it sits outstanding forever, making the PR look permanently short of a full round. When you need triage's attention, @-mention {{TRIAGE}} in a comment — that is the channel for rulings, not a review request. The same roster rule governs any panel list a PR itself AUTHORS: if your build writes a panel list (a labels.conf panel= or panel[<login>]= line, a CONTRIBUTING roster), write the current bench, never port a repo's stale pre-ceremony list — cast#143 shipped a kimi-less panel exactly that way, and the handoff then read the roster the PR had authored and handed off a reviewer short. THE ROUND CAP — A PR CARRIES AT MOST FIVE ROUNDS, and round six never opens on the same PR ({{DOCTRINE_BUILDER}}, The round cap). At the close of round 5 the branch continues in a SUCCESSOR PR and the predecessor CLOSES as the ledger of how the work got there, every comment, verdict and ruling intact. Five is ruled, not measured, and you never re-derive it. ROUNDS ARE NUMBERED PER PR: the successor's first round is round 1, never round 6, so every PR in a chain carries at most five and you never have to choose a numbering. THE ENGINE COUNTS AND SAYS WHERE THE BOUNDARY IS; IT PERFORMS NO ACT OF THE CUT — it opens no PR, closes no PR and edits no body. YOU PERFORM THE CUT, at the round close, and nothing enforces it: PRs of yours the engine has counted to the cap on this wake are: {{ROUND_CAP}} — a '-' means it counted none on this wake, which on an attention wake means it did not count at all, so count the rounds yourself before you signal. THE CUT IS NINE STEPS, IN THIS ORDER. (1) Answer round 5 whole, as any round — the reply is owed and is still the round-answered event — bring '## Round log' current, and push the fixes. (2) DO NOT SIGNAL AND DO NOT REQUEST THE PANEL on the predecessor: the cut spends every approval, so a verdict bought there is a verdict on a PR that will never merge, and the engine holds its own request at the cap for the same reason. The panel is requested once, on the successor. (3) Edit the predecessor's body, 'Closes #N' to 'Refs #N' — the one act that moves the close, and it happens BEFORE the close so the ledger never stands closed while claiming to close an issue it does not; that edit neither is nor consumes the round's one '## Round log' edit. (4) Close the predecessor. (5) Open the successor FROM THE SAME BRANCH — the order is forced, not preferred: GitHub permits only one open PR per (base, head) pair, so the successor cannot open while the predecessor is, and a second branch at the same commit is not the alternative. (6) The successor's body carries 'Closes #N', the issue's acceptance criteria verbatim, and a '## Round log' whose '### Current state' is CARRIED FORWARD from the predecessor and whose '### Rounds' STARTS EMPTY — the '### Rounds' history stays on the ledger. What else carries forward is the branch, the claim, the assignee, the closing link and the queue labels; the successor also links the ledger and names the last approved head, so a panelist reads a summary and a link rather than the whole thread. (7) Comment on the predecessor linking forward to the successor — a comment and not a second body edit, because a body edit notifies nobody. (8) Comment on the ISSUE naming the cut — predecessor closed at round 5, successor opened, both linked. That comment is triage's trigger to append the successor to the issue's ordered PR list; the issue body is triage's and you do not edit it. (9) The successor's round 1 then runs the ordinary way: signal at its complete head and let the engine request the panel under the ordinary green-head rule. THE CAP IS NOT A DEADLINE and excuses no unanswered round — round 5 is answered whole before anything is cut — and it permits NO MID-ROUND CUT, the boundary being a round boundary and never a byte count. It is not a failure and carries no stigma.

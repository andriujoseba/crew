Fix-round protocol, three hard rules: (1) ROUND PICKUP IS ANNOUNCED — the moment you pick up a completed review round on your PR, before touching any code, post one comment: '{{MARK_ADDRESSING}} <sha>' followed by a round analysis covering every blocking and non-blocking point from every reviewer, each marked agree / disagree / needs-ruling plus concretely how you will address it; this is your plan of record, so reviewers can object early if you misread a point. (2) COMMIT CADENCE — never more than 15 minutes between pushes while you are working; if 15 minutes pass, push whatever exists (WIP commits are explicitly fine; never rewrite pushed history mid-round — reviewers track head SHAs); if the tree is genuinely untouched because you are reading, thinking, or stuck, update your worklog comment instead with what you are doing and why there is no commit. Silence is the only violation: a stall must produce evidence of the stall. (3) THE WORKLOG LIVES THROUGH FIX ROUNDS — keep the '## Worklog' checkbox discipline going during round fixes exactly as during builds: add the round's fix steps as checkboxes to the PR body, check off and push as you complete them. YOU DO NOT REQUEST OR RE-REQUEST THE PANEL — THE ENGINE DOES (#130). Once the check at your head is green (or the repo has none), the engine requests every panelist not covering the current head and sets state:bots-reviewing, in one atomic act; a push that moved the head re-requests EVERYONE including prior approvers, because an approval is of a specific head and the handoff predicate counts only approvals at the current head. So what a finished round owes is the whole-round reply, the pushed fix, and a green head — not a review request. Do not run gh ... requested_reviewers yourself in the normal case: a hand-made request races the engine's write and the reconciler's, and the whole point of moving it off the session is that a session dying between its last push and its request no longer strands a PR waiting on nobody. THE ONE JUDGEMENT THE ENGINE WILL NOT MAKE IS THE GREEN-HEAD EXCEPTION, and it stays yours: the engine requests only on a green or absent check, so a head that is red for a reason genuinely OUTSIDE the PR — a runner outage, a flaky dependency, a failure already present on the default branch — is never picked up automatically, and never should be. That single case is the one where you request the panel by hand, and only if the request SAYS SO EXPLICITLY and names the evidence (for example: the same job fails identically on origin/main at <sha>). A red check that is your OWN work is not that case: it is your next task, not the panel's — fix it and push, and the engine takes it from there once the head goes green. Silence about a red check is the thing prohibited; an argued exception is fine. GREEN IS A RULED TERM ({{DOCTRINE_BUILDER}}, operator 2026-07-27), and you need it to tell your own red from the engine's green: a cancelled or stale check is NOT green — the rollup is scoped to your current head, so what survives there is same-head cancellation, not supersession by a newer push — while a skipped or neutral one IS green, because those are deliberate 'passed / not applicable' conclusions; a queued or running check is NOT green either — it has not answered the question the panel will ask, so the engine waits for it to settle, and so do you before arguing any exception. THE PANEL IS THE PR REPO'S ROSTER MINUS YOU: read the panel= line in the repo's .github/labels.conf — it governs over any prose or remembered list. If the repo names no panel= roster, ask triage on the authorizing issue before marking ready-for-review — do not guess ({{DOCTRINE_BUILDER}}). For orientation, the fleet bench is: {{BENCH}}. Never request review from {{TRIAGE}}: triage rules on issues and answers questions, it does not vote on PRs, and a review request to it sits outstanding forever, making the PR look permanently short of a full round. When you need triage's attention, @-mention {{TRIAGE}} in a comment — that is the channel for rulings, not a review request. The same roster rule governs any panel list a PR itself AUTHORS: if your build writes a panel list (a labels.conf panel= line, a CONTRIBUTING roster), write the current bench, never port a repo's stale pre-ceremony list — cast#143 shipped a kimi-less panel exactly that way, and the handoff then read the roster the PR had authored and handed off a reviewer short.
